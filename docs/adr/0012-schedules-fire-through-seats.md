# Schedules are rows in EFFECT_PI_DB and fire through Conversations like a person's send

A User can ask for work later or on a repeat (#77): a follow-up sent into an existing Conversation, or a new Conversation per run from a saved prompt and settings. A Schedule is a row in `EFFECT_PI_DB` (`schedules`, `schedule_runs`, `time_zones`), and a Scheduler fiber fires it by calling `Conversations.send` or `Conversations.create`, the same paths a person's message takes. So a fire claims Capacity, re-seats a paused Conversation, queues behind a running Run and is owned by the schedule's User exactly as if they had typed it.

## Decisions

- **SQLite rows, not pi-durable documents.** A new-conversation schedule belongs to no Conversation, and the Scheduler needs "what is due next" across every User: one indexed column (`wake_at`) instead of scanning every Conversation's document at boot. The file is already replicated by Litestream (ADR-0006).
- **Cron or an instant, in an IANA zone stored on the schedule.** Recurrence is a five-field cron evaluated by Effect's `Cron` with the zone (DST included, no new dependency); a one-time schedule is an instant. RRULE needs a library, and ISO 8601 repeating intervals cannot say "weekdays at 9". The model resolves natural language at write time (`at` as a local date-time, `in_minutes`, or `cron`), told the person's zone and today's date in a prompt section. Each User's zone is reported by their browser; each schedule copies it when made, so a later change never moves an existing schedule silently. Occurrences closer than 5 minutes are refused; at most 50 schedules per User are active or paused.
- **Exactly once across restarts, without a durable timer.** A follow-up's submission carries `requestId` `schedule:<id>:<due>`, so firing it again after a crash is the same submission. A new-conversation fire first records the occurrence it is creating (`firing`), and the Conversation's metadata carries `schedule: { id, due }`, so a restart finds a fire that happened instead of creating a second Conversation.
- **Catch up once after downtime.** An overdue schedule fires one time when the server is back (its run marked `late`), then a recurring one skips to its next occurrence after now. A reminder is still worth sending late; a daily report run five times after a weekend outage is not.
- **A full server is waited out, never evicted.** A fire that meets `CapacityExhausted` retries after 1, 2, 4, 8, then every 15 minutes, for at most an hour or until the next occurrence; then the occurrence is recorded `missed` with the limit it hit. Pausing someone's Seat to make room would break ADR-0001's rule that nothing is evicted.
- **Marked as scheduled where the model and the console read it.** The fired message leads with a `<scheduled_run>` block (after `/skill:` expansion, so a saved skill prompt still forces its skill; typed text cannot forge one), and the `schedule:` requestId marks the submission. Run notifications tell a scheduled run by that requestId.
- **The agent schedules, its subagents do not.** The `schedule` tool's create and cancel wait for approval under `ask` (`withApproval` with a `when` predicate; list does not wait). A subagent has the tool removed: a schedule would outlive the task that made it, and a follow-up into a task-owned child has no Seat to land in. An agent's new-conversation schedule takes its conversation's Level, Software and approval policy; the console's default is `auto`, since nobody watches a scheduled run start.

## Consequences

A scheduled run under `ask` holds its Seat while it waits for a person, like any other Run. The model is not a schedule setting: a scheduled Conversation gets the server's configured model.
